# 4. 설계

## 아키텍처

- 최초 스캐폴딩(커밋 `d168be7`, 본인 작성)은 Feature-Sliced Design(FSD) 스타일로 `src/app`(라우팅/프로바이더), `src/entities`(도메인 모델), `src/features`(기능 단위 UI), `src/shared`(공통 UI/설정)로 구성되어 있었습니다.
- 이후 본인이 커밋 `9c9e203`/`475a930`("디렉토리 구조 변경 (#1)")에서 이를 화면 중심 구조로 재편했습니다: `src/pages`(화면), `src/components`(도메인별 UI 조각), `src/stores`(Zustand), `src/hooks`, `src/router`(expo-router 엔트리), `src/api`(백엔드 연동), `src/styles`. 이 변경은 파일 46개, 330줄 삭제(rename 포함)로 반영되었습니다(근거: `git show 9c9e203 --stat`).
- 요청 처리 흐름은 다음과 같습니다.
  1. `src/router/*.tsx`가 expo-router의 파일 기반 라우팅 진입점 역할을 하며 실제 화면 컴포넌트를 `src/pages/*`에서 가져와 렌더링합니다(예: `src/router/map.tsx` → `src/pages/map.tsx`).
  2. 화면 컴포넌트는 필요 시 `src/hooks/use-*.ts`(TanStack Query 훅)를 호출해 서버 데이터를 가져오거나, `src/stores/*.ts`(Zustand)에서 로컬 상태를 읽고 씁니다.
  3. TanStack Query 훅은 `src/api/*.ts`의 도메인 함수(`getCourses`, `getMyInvitations` 등)를 `queryFn`으로 사용합니다.
  4. 도메인 함수는 공통 클라이언트 `src/api/client.ts`의 `get/post/put/patch/del`을 호출합니다.
  5. 공통 클라이언트는 `fetch`로 실제 백엔드(`EXPO_PUBLIC_API_URL`)에 요청하고, 실패 시(네트워크 오류, HTTP 에러, `isSuccess:false`) 자동으로 내장된 Mock 데이터로 폴백합니다.

```text
router/*.tsx (expo-router 엔트리)
  → pages/*.tsx (화면)
    → hooks/use-*.ts (TanStack Query: 서버 상태)  ─┐
    → stores/*.ts (Zustand: 로컬/편집 상태)        │
                                                    ↓
                                            api/*.ts (도메인 함수)
                                                    ↓
                                        api/client.ts (get/post/put/patch/del + Mock Fallback)
                                                    ↓
                                        fetch(EXPO_PUBLIC_API_URL + path)
```

## 데이터 모델

- 이 레포는 프론트엔드 전용이라 DB 스키마나 ORM 엔티티는 없으며, 대신 백엔드 응답 계약을 TypeScript 인터페이스로 프론트엔드에서 재정의해 사용합니다. 주요 타입은 다음과 같습니다.
  - `CourseDetailResponseDto`(`src/api/course.ts`): `courseId`, `name`, `dates: CourseDateDetailDto[]` 구조로, 하루 단위(`date`) 안에 장소 배열(`places: CoursePlaceDetailDto[]`)을 담는 계층 구조입니다. 각 장소는 `orderType: 'START' | 'WAYPOINT' | 'END'`로 여정 내 역할을 구분합니다.
  - `CourseInvitationResponseDto`(`src/api/invitation.ts`): 초대 1건에 대해 `courseMemberId`, `courseId`, `status: 'PENDING' | 'ACCEPTED' | 'REJECTED'`를 가지며, 신규 필드(`inviterName`/`inviterEmail`)와 구 필드(`counterpartNickname`/`counterpartEmail`, `@deprecated`)가 공존합니다.
  - `WeatherResDTO`(`src/api/weather.ts`): 현재 날씨(`WeatherOnlyResDTO`)에 추천 장소 목록(`places: PlaceSummary[]`)을 확장한 구조입니다.
- "인덱스 설계"는 백엔드 저장소가 아니므로 해당 사항이 없습니다. 대신 프론트엔드 로컬 상태에서 `Record<number, DayPlan>`(`src/stores/dayPlanningStore.ts`)처럼 날짜 인덱스를 키로 쓰는 lookup 구조가 사용되어, 특정 날짜의 일정을 O(1)로 접근하도록 설계되어 있습니다.

## API 및 인터페이스

- 엔드포인트는 도메인별 파일(`api/course.ts`, `api/invitation.ts`, `api/weather.ts`, `api/place.ts`, `api/auth.ts`)로 나뉘고, 각 함수 상단에 JSDoc 스타일 주석으로 `METHOD /path — 설명`을 적는 컨벤션을 따릅니다(예: `/** GET /courses/{courseId} — 코스 상세 조회 */`).
- 응답 규격은 `{ isSuccess: boolean; code: string; message: string; data: T }` 형태의 공통 래퍼(`ApiResponse<T>`, `src/api/client.ts`)를 따르며, 클라이언트 함수는 `isSuccess`가 `false`면 `message`를 담아 `Error`를 던집니다.
- 예외적으로 `src/api/dto/client.ts`(도메인: `createCourse`, `searchPlaces`)는 `ApiResponse` 래퍼를 쓰지 않고 자체 fetch 로직과 자체 Mock 데이터를 별도로 구현하고 있어, `src/api/client.ts` 및 `src/api/course.ts`와 로직이 중복됩니다. (8장 회고에서 상세 서술)
- 에러 처리는 각 HTTP 메서드 래퍼(`get/post/put/patch/del`)의 `try/catch`에서 처리하며, 1차로 원 에러를 로깅(`console.warn`)하고 2차로 Mock 데이터 폴백을 시도합니다. Mock 폴백에서도 처리할 수 없는 경로면 원래 에러를 다시 던집니다.

# 5. 핵심 구현

## API 클라이언트의 Mock Data Fallback 전략

**무엇을 구현했는가**

백엔드 API가 아직 없거나 응답에 실패하는 상황에서도 화면 개발과 시연이 끊기지 않도록, 모든 HTTP 요청 함수(`get`, `post`, `put`, `patch`, `del`)에 실패 시 내장 Mock 데이터로 자동 전환되는 폴백 로직을 구현했습니다.

**어떻게 구현했는가**

1. `src/api/client.ts`의 각 HTTP 함수는 우선 실제 `fetch`로 백엔드에 요청합니다.
2. 응답이 `!res.ok`이거나 `json.isSuccess`가 `false`이면 `Error`를 던져 `catch` 블록으로 넘어갑니다.
3. `catch` 블록에서 `console.warn`으로 실패를 로깅한 뒤, `getMockDataFallback(method, path, body)`를 호출합니다.
4. `getMockDataFallback`은 요청 경로(`path`)를 문자열 패턴으로 분기해(`path === '/courses'`, `path.startsWith('/api/weather/')` 등) 해당 도메인에 맞는 고정 Mock 데이터 또는 요청 바디를 반영한 동적 Mock 데이터를 반환합니다.
5. Mock 데이터로도 처리할 수 없는 경로는 `지원하지 않는 Mock API 경로입니다` 에러를 던지고, 최종적으로 원래 네트워크 에러가 호출부에 전파됩니다.

**선택지와 판단**

- 대안으로는 MSW(Mock Service Worker)를 붙이는 방법이 있었고 실제로 `README.md`에는 MSW 기반 `bootstrap/`, `mocks/` 구조가 문서화되어 있었으나, 최종 구현에서는 자체 Mock Fallback 함수로 대체되었습니다. MSW 대비 네트워크 계층을 가로채지 않고 애플리케이션 코드 안에서 직접 처리하기 때문에 설정 비용은 적지만, Mock 데이터가 `client.ts` 한 파일에 집중되어 파일이 비대해지는 트레이드오프가 있습니다(해당 시점 기준 300줄 이상). 이 트레이드오프에 대한 팀 논의 근거는 찾지 못했습니다. (확인 필요)

**코드 발췌**

```typescript
// src/api/client.ts
export async function get<T>(path: string): Promise<T> {
  const baseUrl = getApiBaseUrl();
  try {
    const res = await fetch(`${baseUrl}${path}`, { method: 'GET', headers: getHeaders() });
    if (!res.ok) throw new Error(`HTTP error ${res.status}`);
    const json: ApiResponse<T> = await res.json();
    if (!json.isSuccess) {
      throw new Error(json.message || '요청에 실패했습니다.');
    }
    return json.data;
  } catch (err) {
    console.warn(`[API GET FAIL] Falling back to mock data for ${path}:`, err);
    try {
      return getMockDataFallback('GET', path) as T;
    } catch {
      throw err;
    }
  }
}
```

## 크로스플랫폼 지도 렌더링 분기 처리

**무엇을 구현했는가**

동일한 지도 화면(`src/pages/map.tsx`)이 웹, iOS/Android에서 각각 다른 렌더링 방식으로 동작하도록 조건부 분기를 구현했습니다.

**어떻게 구현했는가**

1. 모듈 최상단에서 `Platform.OS !== 'web'`일 때만 `require('react-native-webview').WebView`를 시도하고, 실패하면 `WebView`를 `null`로 유지합니다(웹 번들에 네이티브 전용 모듈이 섞여 들어가는 것을 방지).
2. 렌더링 시점에 `Platform.OS === 'web'`이면 `<iframe src={mapUrl}>`을, 네이티브에서 `WebView`가 로드됐으면 `<WebView source={{ uri: mapUrl }}>`을, 둘 다 불가능하면 안내 텍스트를 보여주는 3단 분기를 둡니다.
3. `mapUrl`은 `useMemo`로 선택된 장소명을 카카오맵 검색 링크(`https://map.kakao.com/link/search/...`)로 인코딩해 구성합니다.

**선택지와 판단**

- 대안으로 `react-native-maps`나 카카오맵 네이티브 SDK를 붙여 지도 위에 마커/제스처를 직접 그리는 방식이 있었을 것으로 보이나, 카카오맵의 웹 검색 링크를 `iframe`/`WebView`로 그대로 띄우는 방식을 택했습니다. 네이티브 SDK 대비 API 키 발급, 네이티브 모듈 설치 없이 빠르게 지도 화면을 완성할 수 있는 대신, 지도 위 마커 클릭이나 커스텀 오버레이 같은 상호작용은 제공하지 못하는 한계가 있습니다. 이 트레이드오프에 대한 팀 논의 근거는 찾지 못했습니다. (확인 필요)

## Zustand 스토어 단위 테스트

**무엇을 구현했는가**

`homeStore`, `mapStore`, `mypageStore`, `routeStore` 4개 Zustand 스토어에 대해 `beforeEach`로 상태를 초기화하고 각 액션 호출 후 상태 변화를 검증하는 단위 테스트를 작성했습니다.

**어떻게 구현했는가**

1. `useXStore.setState(...)`로 매 테스트 전 스토어 상태를 고정된 값으로 리셋합니다.
2. `useXStore.getState().액션(...)`을 직접 호출해 React 렌더링 없이 스토어 로직만 검증합니다.
3. 배열 순서 변경(`movePlaceUp`/`movePlaceDown`), 필터링(`addPlaceToRoute`가 `recommendations`에서 항목을 제거), id 기반 갱신(`updateRouteItinerary`) 등 상태 전이 로직을 케이스별로 검증합니다.

**선택지와 판단**

- 컴포넌트 렌더링을 포함하는 RNTL 통합 테스트 대신 스토어 로직만 분리해서 테스트하는 방식을 택해, UI 변경에 테스트가 영향받지 않고 상태 전이 로직만 빠르게 검증할 수 있게 했습니다. 이 판단은 테스트 코드의 구조(컴포넌트 import 없이 스토어만 import)로 확인되나, 명시적으로 문서화된 근거는 없습니다.
