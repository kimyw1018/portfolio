동행 유형별 제주 올레길 여행 코스 플래너, Expo(React Native) 기반 모바일 앱

제주 올레길과 여행지를 혼자 · 가족 · 친구 · 애인 · 배리어프리 · 반려동물 등 동행 유형별로 탐색하고, 날짜별 일정을 짜서 다른 사용자를 초대할 수 있는 여행 플래너 앱입니다. 4인 팀 중 프론트엔드를 담당하며 초기 아키텍처 설계, API 클라이언트, 홈/지도/마이페이지 화면, 여행 초대 연동, 스토어 단위 테스트를 맡았습니다.

01Role
4인 팀에서 프론트엔드를 전담했습니다. 프로젝트 초기 구조(Feature-Sliced Design 스캐폴딩 후 화면 중심 구조로 재편)를 설계하고, Mock Fallback을 포함한 API 클라이언트 아키텍처, 홈 · 지도 · 마이페이지 화면, 여행 초대 API 연동, Zustand 스토어 단위 테스트를 작성했습니다. 전체 34개 커밋 중 12개(약 35%)를 작성했고, 현재 TS/TSX 파일 95개 중 44개(약 46%)를 최초로 작성했습니다. src/ 기준 순변경량은 삽입 7,892줄 · 삭제 1,955줄입니다.
02Stack & Scope
01

02

상태 관리: 클라이언트 로컬 상태는 Zustand, 서버 데이터는 TanStack Query로 분리해 캐시 무효화를 관리.

03

코드 품질: Biome로 린트/포맷을 통일하고, Jest + jest-expo + React Native Testing Library로 스토어 단위 테스트를 작성.

04

담당 영역: src/api/client.ts(API 클라이언트), src/pages/home.tsx · map.tsx · mypage.tsx, src/api/invitation.ts 확장, src/stores/__tests__/ 4개 파일 19개 테스트 케이스(299줄).

03핵심 구현
01

API 클라이언트의 Mock Data Fallback 전략: 백엔드 명세가 개발 중에도 계속 바뀌는 상황에서 화면 개발과 시연이 끊기지 않도록, 모든 HTTP 요청 함수(get/post/put/patch/del)에 실패 시 내장 Mock 데이터로 자동 전환되는 폴백 로직을 구현했다. MSW 기반 구조가 README에 문서화되어 있었지만, 설정 비용이 적은 자체 Mock Fallback 함수로 최종 구현을 대체했다.

02

FSD에서 화면 중심 구조로의 재구조화: 초기에 채택했던 Feature-Sliced Design(app/entities/features/shared)을 팀 규모와 화면 수 대비 과도한 추상화로 판단해, pages/components/stores/hooks/api 중심의 단순한 구조로 전면 재편했다. 46개 파일을 이동·삭제하며 "공유 코드 vs 화면 전용 코드" 구분을 "공통 UI vs 도메인별 UI" 구분으로 바꿨다.

03

크로스플랫폼 지도 렌더링 분기: 동일한 지도 화면이 웹과 iOS/Android에서 다르게 동작하도록 Platform.OS 기준으로 분기했다. 웹은 <iframe>으로, 네이티브는 react-native-webview의 WebView로 카카오맵 검색 링크를 그대로 띄워, 네이티브 SDK 설치 없이 빠르게 지도 화면을 완성했다.

04

여행 초대 API와 하위 호환 DTO 설계: 백엔드 응답 필드명이 counterpartNickname/Email에서 inviterName/Email로 바뀌는 과정에서, 구 필드를 삭제하지 않고 @deprecated 주석과 함께 공존시켜 이미 그 타입을 참조하는 다른 화면의 컴파일이 깨지지 않도록 방어했다.

05

Zustand 스토어 단위 테스트: 홈 · 지도 · 마이페이지 · 경로 스토어 4개에 대해 setState로 매 테스트 전 상태를 리셋하고 getState().액션(...)을 직접 호출해, 컴포넌트 렌더링 없이 배열 순서 변경이나 필터링 같은 상태 전이 로직만 빠르게 검증했다.

04회고

이 레포는 명시적인 버그 수정 커밋이 발견되지 않아, 재현 가능한 "문제 → 원인 → 해결" 형태의 트러블슈팅 사례 대신 솔직한 회고로 남깁니다.

API 클라이언트가 두 갈래로 공존했다: 직접 작성한 src/api/client.ts(ApiResponse 래퍼 기반)와 팀원이 작성한 src/api/dto/client.ts(자체 fetch + 자체 Mock)가 createCourse, searchPlaces 같은 유사 기능을 각자 구현하고 있었다. 처음부터 팀 전체가 합의한 단일 클라이언트로 만들었다면 중복을 피할 수 있었을 것이다.

문서와 실제 구현이 어긋났다: README의 기술 스택 설명("Expo SDK 57, React Native 0.86")이 package.json의 실제 버전(Expo ~54.0.0, React Native 0.81.5)과 달랐고, MSW 기반 구조 설명도 실제로는 client.ts 내장 Mock Fallback으로 대체된 상태였다. 설계를 바꾸면 문서도 같은 PR에서 갱신하는 습관이 필요했다.

테스트 범위가 좁았다: 단위 테스트가 Zustand 스토어에만 있고, 경로 문자열 분기가 많아 회귀 위험이 큰 getMockDataFallback 같은 함수에는 테스트가 없었다. 다음에는 회귀 위험이 큰 분기 로직을 우선순위로 먼저 테스트했을 것이다.
