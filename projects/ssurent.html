04Problem Solving
Deploy & Filesystem Windows vs Vercel

로컬(Windows)에서는 되는데 Vercel 배포에서만 깨지는 import

대소문자를 구분하지 않는 Windows와, 구분하는 Vercel(Linux) 간의 파일명 불일치였다.

문제

통계 페이지(AdminStatistics.tsx) 관련 import가 로컬에서는 정상 동작하지만 Vercel 배포에서만 깨졌다. 팀원이 먼저 만든 useGetStatistics.ts(소문자)와, 같은 훅을 모르고 다시 만든 UseGetStatistics.ts(대문자) 두 파일이 저장소에 공존하고 있었다.

해결

Windows는 파일시스템이 대소문자를 구분하지 않아 로컬에서는 어느 경로든 해석되지만, Vercel의 Linux 빌드 환경은 구분한다. import 경로를 실제 파일명(대문자)에 맞춰 수정한 뒤, 중복된 소문자 파일 자체를 삭제해 재발 소지를 없앴다. 

- import { useGetStatics } from '../../../hooks/useGetStatistics';
+ import { useGetStatics } from '../../../hooks/UseGetStatistics';
결과: 배포 환경에서의 import 해석 실패 해결, 이후 동일 원인 재발 없음
API Client 204 No Content

빈 응답 본문에서 JSON.parse가 터지는 공통 클라이언트

상태 변경·삭제류 API의 204 응답을 선판별해 빈 바디 파싱을 건너뛰도록 고쳤다.

문제

공통 API 클라이언트(Client.ts)가 모든 응답에 대해 항상 response.json()을 호출하도록 되어 있어, 상태 변경이나 삭제처럼 바디가 없는 204 응답을 반환하는 API를 호출하면 Unexpected end of JSON input 파싱 오류가 날 수 있는 구조였다.

해결

응답 상태코드가 204이거나 content-length가 0이면 즉시 null을 반환하고, 그렇지 않으면 response.text()로 먼저 읽어 빈 문자열이면 null, 아니면 JSON.parse를 수행하도록 바꿨다. 

- return response.json();
+ if (response.status === 204 || response.headers.get('content-length') === '0') {
+   return null as unknown as T;
+ }
+ const text = await response.text();
+ return text ? JSON.parse(text) : (null as unknown as T);
결과: 빈 바디 응답을 반환하는 모든 관리자 CRUD API에서 파싱 예외 제거
