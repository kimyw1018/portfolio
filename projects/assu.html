04Problem Solving
Database & GIS 쿼리 격리

지도 조회 시 DB CPU 90% 초과, PostGIS 공간 인덱스로 격리

공간 연산과 권한 검증을 분리하고 IN절 벌크 조회로 N+1을 없앴다.

문제

지도를 드래그하거나 확대할 때 화면 영역(Bounding Box) 안의 매장과 제휴 혜택을 조회하는 쿼리가 공간 연산(ST_MakeEnvelope)과 권한 검증(회비 납부 여부, 활성 제휴 여부)을 다중 JOIN으로 한 번에 처리하고 있었다. DB CPU 점유율이 90%를 넘었고 연관 엔티티 N+1 조회가 폭증했다.

해결

DB는 PostGIS R-Tree 공간 인덱스(GIST)로 뷰포트 안 매장 ID만 추출하도록 역할을 좁혔다. 권한 검증은 애플리케이션 메모리(HashSet O(1))로 옮겼고, 하위 제휴 데이터는 WHERE store_id IN (...) 한 번의 벌크 쿼리 후 Stream groupingBy()로 조립해 N+1을 없앴다.

결과: 지도 API 응답 속도 개선, DB CPU 부하 70% 이상 절감
Query Tuning 83% 개선

데이터가 쌓일수록 느려지는 주간 매장 순위 쿼리

복합 인덱스와 CTE, Window Function으로 단일 쿼리 집계로 바꿨다.

문제

매장별 사용 이력을 개별 조회한 뒤 WAS 메모리에서 정렬하거나, 집계 서브쿼리를 반복 호출하는 구조였다. 데이터가 쌓일수록 O(N)으로 응답 속도가 떨어졌다.

해결

(created_at, store_id) 복합 인덱스로 주차 범위 검색과 매장 그룹핑이 인덱스 트리 안에서 끝나도록 만들었다. WITH weekly_usage AS (...) CTE로 집계를 먼저 격리하고 RANK() OVER (ORDER BY usage_count DESC)로 순위를 단일 SQL에서 한 번에 산출했다.

결과: 주간 순위 집계 쿼리 실행 속도 83% 개선
Concurrency 정합성 100%

동시 요청 시 사라지는 잔여 수량, 비관적 락으로 방어

선착순 혜택 차감의 Lost Update를 행 단위 잠금으로 막았다.

문제

선착순 한정 할인 혜택에 여러 학우가 동시에 사용을 요청하면, 같은 시점의 잔여 수량을 각자 읽고 덮어써서 실제보다 적게 차감되거나 정합성이 깨질 위험이 있었다.

해결

충돌 빈도가 높고 정합성이 필수인 도메인이라 재시도 오버헤드가 큰 낙관적 락 대신 SELECT ... FOR UPDATE를 적용했다. 인덱스를 연계한 행 단위 잠금으로 대상 레코드만 선별해 잠그고 검증 후 바로 커밋해 대기 지연을 최소화했다.

결과: 동시 요청 테스트에서 잔여 수량 차감 정합성 100% 확인
Network & Security 스레드 풀 분석

STOMP 핸들러에서 인증 정보가 사라지는 이유

ThreadLocal 기반 SecurityContext가 STOMP 스레드 풀로 복사되지 않는 구조를 확인했다.

문제

실시간 채팅을 만들면서 기존 HTTP API처럼 메시지 핸들러에 @PreAuthorize를 붙이자 인증 정보가 누락됐다. Spring Security의 SecurityContextHolder는 ThreadLocal 기반인데, STOMP는 비동기 스레드 풀을 써서 인입 스레드와 핸들러 스레드가 분리되어 컨텍스트가 복사되지 않는 게 원인이었다.

해결

웹소켓은 최초 연결(CONNECT) 시점에 JWT를 검증해 세션을 맺으므로, 세션이 수립된 뒤에는 핸들러 레벨의 중복 검증이 필요 없다는 점을 확인했다. 이 내용을 문서로 정리해 팀에 공유하고, 일반 HTTP 엔드포인트에만 검증을 선별 적용하기로 했다.

교훈: 프레임워크 밑단의 스레드 풀 모델을 이해하고 근거로 팀과 조율했다
Kubernetes & Network L4 프로토콜

노드 간 파드 통신 타임아웃, 원인은 보안그룹 UDP 포트

Flannel VXLAN 8472 포트가 TCP로 열려 있어 패킷이 막히고 있었다.

문제

EC2 단일 배포에서 3-Node K3s 클러스터로 옮기던 중 마스터 노드와 워커 노드의 파드 간 통신이 계속 타임아웃됐다. K3s의 Flannel CNI는 노드 간 통신에 VXLAN 캡슐화(8472 UDP)를 쓰는데, AWS 보안그룹에서 관례적으로 8472를 TCP로만 열어둔 게 원인이었다.

해결

보안그룹 인바운드 규칙을 Custom UDP Rule(8472)로 바꿔 VXLAN 터널링을 정상화하고 노드 간 서비스 디스커버리를 복구했다.

교훈: 클라우드 도구 밑단의 전송 프로토콜을 알아야 장애를 예방할 수 있다
Ingress & TLS ACME 챌린지

Let's Encrypt 인증서 발급이 반복 실패한 이유

80/443 엔트리포인트 동시 지정으로 생긴 TLS 리졸버 충돌을 정리했다.

문제

자동 인증서 갱신을 위해 ingress.yaml에 web(80)과 websecure(443)를 동시에 설정했는데 HTTP-01 챌린지가 계속 실패했다. 80 포트에도 TLS 리졸버가 먼저 매칭되어 ACME 챌린지 핸들러보다 우선순위를 가진 라우터가 충돌하고 있었다.

해결

Ingress 엔트리포인트를 websecure(443) 단독으로 지정하고, 80 포트 리다이렉트는 클러스터 전역 미들웨어로 분리해 챌린지 경로를 독립시켰다.

결과: HTTPS 무중단 자동 인증서 갱신 파이프라인 완비
Collaboration 스키마 우선 설계

DTO를 먼저 확정해서 프론트엔드 병렬 개발을 열었다

Swagger와 목업 데이터 선제공, Git Submodule로 민감 설정 분리.

문제

이전에 백엔드의 잦은 DTO·ERD 변경으로 프론트엔드에서 TypeScript 에러를 자주 겪었던 경험이 있었다. 이번에는 그 문제를 반복하고 싶지 않았다.

해결

프론트엔드 화면 구성에 맞춰 데이터 스키마를 먼저 확정하고 Swagger와 목업 데이터를 미리 제공해, 백엔드 배포를 기다리지 않고 병렬 개발이 가능하게 했다. 환경별 설정 파일 관리에는 Git Submodule을 제안해 민감 정보 유출 위험을 없앴고, 동료 업무가 몰릴 때는 관리자·통계 백오피스 API를 전담해 릴리즈 일정을 맞췄다.
