Part 1. [Android] 대시보드 클라이언트 구현

1. 주요 성과 및 기술적 기여

A. 타입 안전 상태 관리 시스템 설계

• Sealed Interface 기반 Exhaustive State Management 구축
• StateFlow 불변성으로 Thread-Safe 반응형 아키텍처 실현
• 성과: 런타임 상태 에러 0건 및 Fragment UI 깜빡임 제거

B. Clean Architecture 멀티 레이어 설계

• Presentation / Domain / Data 레이어 완전 분리
• Repository Pattern + UseCase로 비즈니스 로직 캡슐화 및 DTO-Model 변환
• 성과: 각 레이어 독립적 단위 테스트 및 Mock 서버 연동 가능

C. 병렬 API 호출 최적화

• Kotlin Coroutines async/await로 독립된 3개 API 동시 호출
• coroutineScope Structured Concurrency 보장 및 부분 실패 대응
• 성과: 네트워크 I/O 대기 시간 중복 제거 및 체감 속도 향상

D. Retrofit + Hilt 네트워크 계층 구축

• Moshi JSON 직렬화 및 HttpLoggingInterceptor 로깅
• AuthInterceptor로 SharedPreferences 토큰 Header 자동 탑재
• Qualifier Annotation으로 BaseUrl 및 Interceptor 모듈 분리

2. 안드로이드 트러블 슈팅 (Deep Dive)

Issue 1

ViewModel 상태 관리 불일치로 인한 컴파일 에러

원인: PartnerDashboardUiState를 Sealed interface와 data class로 중복 정의하여 Fragment와 ViewModel 간 타입 충돌 발생.
해결: Sealed interface를 독립 타입으로 ViewModel 외부로 분리하고, StateFlow 이름을 dashboardState로 통일. Success 상태 헬퍼 함수(getCurrentData()) 구현으로 컴파일 타임에 모든 상태 처리 강제.

Issue 2

Repository 계층의 Service 인터페이스 미정의 문제

원인: Repository 구현체에서 StoreService, AdminService를 주입받으나 실제 인터페이스 정의 및 Hilt Module Provider 등록 누락으로 DI 런타임 에러 발생.
해결: 완전한 Retrofit HTTP 어노테이션(@GET, @POST) 정의, Moshi DTO의 toModel() 확장 함수 구조화, NetworkModule과 RepositoryModule의 @Binds 바인딩 구성 완료.

Issue 3

차트 데이터 업데이트 시 UI 미반영 문제

원인: 사용자가 주차를 선택해도 MPAndroidChart 막대 색상이 변경되지 않음 (Fragment에서 selectedWeekIndex 미수신 및 DataSet 색상 변경 후 뷰 리렌더링 파이프라인 누락).
해결: Fragment의 StateFlow Observation 추가, updateBarColors() 호출 및 invalidate() 연동, 모서리가 둥근 커스텀 렌더러(RoundedBarChartRenderer) 적용으로 완전한 UI 동기화 달성.

Part 2. [Spring Boot] 백엔드 API & 클라우드 인프라

1. 주요 성과 및 기술적 기여

A. 도메인 모델 설계 및 통계 집계 최적화

• Student-Store N:M을 partnership 연결 엔티티로 정규화
• CTE(Common Table Expression) 및 RANK() OVER Window 함수로 주차별 순위 단일 쿼리 일괄 집계
• 복합 인덱스 설계: 통계 쿼리 O(N) → O(log N) 개선

B. 공간 인덱싱(GIS) 및 지도 API 최적화

• 프론트 뷰포트를 WKT(POLYGON)로 변환해 PostGIS R-Tree 인덱스 연동
• 역할 분담: DB는 공간 바운딩 박스 필터링만 전담, 제휴 권한 검증은 WAS 메모리(HashSet O(1))로 이관
• IN 절 Bulk Read + Stream groupingBy로 N+1 문제 원천 차단

C. 실시간 통신 및 동시성 제어

• STOMP WebSocket CONNECT 시점에 JWT 사전 검증
• 제휴 사용량 동시 업데이트 시 집계 누락(Lost Update) 방지를 위해 DB 비관적 락(SELECT ... FOR UPDATE) 적용
• 트랜잭션 범위를 최소화하여 락 경합 방어

D. K3s 기반 GitOps 배포 및 클러스터 아키텍처

• GitHub Actions → Manifest 커밋 → ArgoCD K3s 자동 동기화
• 3-Node 클러스터: Control 노드(Taint 격리), Prod 노드, Dev 노드 분리
• Git Submodule로 민감 설정 격리 및 단일 RDS 스키마 분리

2. 백엔드 & 인프라 트러블 슈팅 (Deep Dive)

Issue 1

동시성 트랜잭션으로 인한 집계 데이터 누락 (Lost Update)

원인: 락 없이 단순 READ → UPDATE를 수행하여 다수 학생이 동시에 같은 매장의 제휴 사용량을 올릴 때 이전 트랜잭션의 커밋이 덮어씌워짐.
해결: 통계 정합성 보장을 위해 낙관적 락 대신 비관적 락(@Lock(LockModeType.PESSIMISTIC_WRITE))을 적용하고, 행 단위 잠금(Row-level Lock) 유지 및 트랜잭션 범위 최소화로 락 유지 시간 단축.

Issue 2

STOMP 실시간 통신 시 SecurityContext 누락 문제

원인: SecurityContextHolder의 ThreadLocal 기반 컨텍스트가 STOMP 비동기 ThreadPoolTaskExecutor 워커 스레드로 전파되지 않아 @PreAuthorize 인가 실패 발생.
해결: STOMP 수명주기상 CONNECT 시점에 JWT가 사전 검증되므로 핸들러 레벨의 중복 검증을 제거하고, 요청 단위 인증이 필요한 HTTP 엔드포인트에만 선별 적용하여 컨텍스트 복사 오버헤드 제거.

Issue 3

Flannel 오버레이 프로토콜 오설정 및 Traefik 충돌

원인: AWS 보안그룹에서 Flannel VXLAN 포트 8472를 TCP로 개방하여 노드 간 파드 통신 타임아웃 발생 (Flannel은 UDP 기반).
해결: 8472 인바운드를 UDP로 수정하고, Traefik 인그레스 엔트리포인트를 websecure 단독 지정 및 인프라 레벨 HTTPS 리다이렉트 위임으로 통신 및 인증서 발급 정상화.
