1. 기술적 구현 방식 (Technical Implementation)

A. 브라우저 부하 격리를 위한 분리 녹화 아키텍처

기존 합성 방식의 한계: Canvas API 위에 고해상도(1080p) 슬라이드와 웹캠 비디오를 얹어 실시간 합성 인코딩 시 브라우저 CPU 부하 급증 및 5분 이상 녹화 시 메모리 누수로 브라우저 탭 다운 발생.

구조적 개선: 화면 합성 방식을 배제하고 [웹캠 스트림 독립 녹화(640x480, VP9) + 슬라이드 전환 타임스탬프 메타데이터 분리 수집] 구조로 전면 전환.

[ 기존 합성 방식 ]
[슬라이드] + [웹캠] ──(Canvas 합성 / 1080p)──> [통짜 대용량 영상] (메모리 폭증 및 크래시 발생)

[ 개선된 분리 방식 ]
├── [웹캠 스트림] ──(MediaRecorder / 480p)──> [경량 비디오 Blob] (저용량 웹캠 단독 캡처)
└── [슬라이드 조작] ──(타임스탬프 기록) ──> [JSON 메타데이터] (텍스트 데이터로 분리 저장)

✨ 성과: 장시간 녹화 시 브라우저 크래시 0건 달성 및 슬라이드 정적 렌더링으로 텍스트 선명도 100% 보존

B. 3-Phase 청크(Chunk) 업로드 파이프라인

문제: 5분 이상의 영상 단일 전송 시 네트워크 지연 및 패킷 유실로 HTTP 타임아웃 빈발, 실패 시 처음부터 다시 전송해야 하는 비효율 발생.

해결책: 1MB 단위의 Blob 청크로 분할하여 순차 전송하고 실시간 진행률 시각 피드백 제공.

Phase 1: Start

총 청크 수 & 메타데이터 전송 → 고유 videoId 발급

Phase 2: Chunks

1MB 단위 순차 POST 전송 및 실시간 업로드 진행률 계산

Phase 3: Finish

슬라이드 전환 타임라인 전송 → 서버 병합 및 HLS 트랜스코딩 시작

C. Zustand 기반 비디오 동기화 엔진

요구 조건: <VideoPlayer>의 현재 재생 시간(currentTime)에 맞춰 <SlideViewer>, <ScriptSection>, <CommentList>가 밀리초 단위로 지연 없이 동기화되어야 함.

해결책: Context API의 트리 전체 리렌더링 병목을 방지하기 위해 경량 상태 관리 라이브러리인 Zustand 채택. 재생 시간 업데이트(updateCurrentTime)와 특정 시점 탐색(seekTo)을 스토어 레벨에서 단일 진실 공급원(SSOT)으로 통제.

2. 기술 스택 선택 근거 (Tech Stack Rationale)

기술 스택 선택 이유 대안 비교
TypeScript 슬라이드 타임라인, 청크 메타데이터, API DTO 간 엄격한 타입 계약 보장 런타임 타입 에러 및 스키마 변경 시 디버깅 비용 방지
Zustand 보일러플레이트가 적고 셀렉터 기반으로 불필요한 리렌더링 차단 Context API의 전체 리렌더링 및 Redux의 과도한 보일러플레이트 배제
TanStack Query 영상 목록, 처리 상태 폴링, 비동기 상태 캐싱을 선언적으로 처리 useEffect + useState 수동 관리 시 발생하는 경쟁 상태(Race Condition) 방지
hls.js 브라우저 환경에서 HLS 스트리밍을 안정적으로 제어할 수 있는 표준 라이브러리 표준 <video> 태그의 브라우저별 HLS 호환성 한계 해결
